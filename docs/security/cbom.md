# 暗号の一覧（CBOM）

- 作成：2026-11-04（19日目、KIDS-63）。脅威分析の T-31、対策 C-34 (1)
- 機械で読める形：[cbom.cdx.json](cbom.cdx.json)（CycloneDX 1.7 の暗号の部品）
- 目的：どこで、どの暗号を、誰が決めているかを1か所にまとめ、量子コンピューターへの備え（PQC への移行）で、入れ替える場所をすぐに探せるようにする
- 範囲：このリポジトリのコード、設定、開発の流れ（Git、CI）で使う暗号。AWS（14日目に削除）は「過去」として残す
- 量子への強さ：NIST の安全性の区分（0〜5）。0 は「量子コンピューターで破られる」。共通鍵とハッシュは、量子でも鍵の長さを2倍にすれば足りるとされ、区分が付く

## 分かったこと

- **鍵交換は、自分で決める場所が少ない**：公開の配信（#1）は、GitHub がすでにハイブリッドにしていた。自分で決める TLS は #3 と #4 だけで、#4 は方式を確かめていない
- **同じ相手でも、道具の版で方式が変わる**：GitHub への SSH（#7）は、Windows の OpenSSH 9.5 では従来の方式、Git for Windows の OpenSSH 10.6 ではハイブリッドだった。サーバーが対応していても、クライアントの版が古いと PQC にならない。車載で言えば、ゲートウェイが新しい方式に対応しても、診断の道具の側が古ければ古い方式で通信するのと同じ
- **署名は、どれも量子への強さが 0**：トークン、パスキー、cosign、証明書、SSH の鍵。署名の移行（ML-DSA）は、規格や道具の対応を待つものが多い。署名は「将来解読」の対象ではなく、偽造は量子コンピューターができてからの問題なので、鍵交換より後でよいとされる
- **「決める人」の列が大事**：13件のうち、自分で決められるのは6件ほど。残りは GitHub、ブラウザ、認証器、Sigstore が決める。車載でも、HSM、ライブラリ、仕入れ先、認証局の対応を待つ部分があり、それを一覧で見える化するのが CBOM の役目
