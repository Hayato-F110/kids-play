# CAN の模擬ログの異常検知（19日目）

- 日付：2026-11-04（KIDS-63）
- 道具：[tools/canids/](../../tools/canids/)（Python でログを作り、DuckDB の SQL で検知する）
- 題材：スクリプトで作った架空のログだけ。実車や会社のログは使わない。ID、周期、値の意味は、学習のために自分で決めた

## ログ

| ID | 意味（架空） | 周期 | DLC |
|---|---|---|---|
| 0x100 | 車速（0.01 km/h 単位、先頭の2バイト） | 10 ms | 8 |
| 0x200 | エンジンの回転数 | 20 ms | 8 |
| 0x300 | ドア | 100 ms | 2 |
| 0x400 | 水温 | 1000 ms | 4 |

- 60秒、9920 フレーム。乱数の種は 1。時刻の揺れ（ジッター）は周期の ±3% まで
- 最初の20秒は異常を入れない（検知の側が「ふだん」を学ぶ区間）。残りの40秒に、5種類の異常を別々の時間帯に入れた

| 異常 | 入れ方 | 数 |
|---|---|---|
| dos | 最も優先度の高い ID 0x000 を 1 ms ごとに流す | 200 |
| spoof | 0x100 のなりすましを、本物の 2〜8 ms 後に差し込む。値は本物と同じ（もっともらしい） | 50 |
| unknown_id | 設計にない ID 0x7FF | 10 |
| dlc | 0x200 の長さを 8 から 4 に変える | 10 |
| jump | 車速を1フレームだけ 250 km/h にする | 5 |

## 検知の規則（DuckDB の SQL）

学習の区間で、ID ごとに「周期（間隔の中央値）」と「いつもの長さ（DLC の最頻値）」を決め、そのあとの区間に上から順に当てる。

| 規則 | 条件 | 車載の IDS での呼び方の例 |
|---|---|---|
| unknown_id | 学習の区間に出てこない ID | ID のホワイトリスト |
| dlc | いつもと違う長さ | 形式の検査 |
| timing | 前のフレームとの間隔が、周期 × しきい値（既定 0.5）より短い | 周期の監視 |
| jump | 車速が1フレームで 20 km/h を超えて変わる | 値の妥当性（物理的にありえない変化） |

前のフレームとの間隔は、SQL の窓関数 `lag(ts) OVER (PARTITION BY can_id ORDER BY ts)` で出した（[detect.py](../../tools/canids/canids/detect.py)）。

## 結果（しきい値 0.5）

| 異常の種類 | 入れた数 | 検知 | 見逃し |
|---|---|---|---|
| dlc | 10 | 10 | 0 |
| dos | 200 | 200 | 0 |
| jump | 5 | 5 | 0 |
| spoof | 50 | 21 | 29 |
| unknown_id | 10 | 10 | 0 |

**誤検知**：正常なフレーム 6424 件のうち 35 件（timing の規則で 30 件、jump の規則で 5 件）

## 間隔の規則のしきい値を変えると

| しきい値 | spoof の検知 | spoof の見逃し | 誤検知（timing） | 誤検知（合計） |
|---|---|---|---|---|
| 0.3 | 5 | 45 | 15 | 20 |
| 0.5 | 21 | 29 | 30 | 35 |
| 0.7 | 36 | 14 | 45 | 50 |
| 0.9 | 50 | 0 | 50 | 55 |

## 分かったこと

1. **形が違う攻撃は、簡単な規則ですべて見つかる**：未知の ID、DoS（未知の ID として見つかった）、長さの違い、ありえない値の跳び。どれも見逃し0件
2. **もっともらしい なりすまし は難しい**：値が本物と同じなので、見分ける手がかりは間隔だけ。しきい値を上げると見逃しは減るが、誤検知が増える（見逃しと誤検知の引き換え）
3. **誤検知は、すべて攻撃のすぐ隣で起きた**：なりすましが1本入ると、前後の本物との間隔が2つとも短くなるので、間隔だけでは「どちらが偽物か」を決められない。値の跳びも、跳びのあとに元へ戻る本物のフレームが、次の誤検知になる。しきい値 0.9 では、なりすまし50回をすべて見つけ、攻撃と関係のない誤報は0件だった。フレームの単位ではなく、「異常が起きた」という出来事の単位で数えると、成績の見え方が変わる
4. **検知では、なりすましを止められない**：IDS は「おかしい」と知らせるだけで、どのフレームが偽物かは分からない。偽物を受け取らないようにするのは、18日目の SecOC（MAC とフレッシュネス）の役目。検知と防御は役割が違い、両方が要る

## 規制と規格との対応

- UN-R155 は、車両への攻撃を検知し、対応できることを求める（車両の外の監視の仕組み、VSOC と組み合わせる）。今日の規則は、その入口にあたる車内の IDS の考え方
- ISO/SAE 21434 の第8章（継続的なサイバーセキュリティの活動）では、監視で集めた情報を評価し、脆弱性として扱うかを決める。誤検知が多いと、評価の手間が増え、本物を見落とす。今日の Dependabot の通知が32件出た件（[php-bbs.md](php-bbs.md)）と同じ問題
- 実際の車載の IDS は、ECU やゲートウェイの限られた計算資源で動く。今日の SQL はログをあとから調べる形（オフラインの分析）で、VSOC の側の分析に近い

## 再現の手順（tools/canids で）

```powershell
uv run python -m canids.generate              # results/can_log.csv を作る（Git の外）
uv run python -m canids.detect                # しきい値 0.5 で検知と評価
uv run python -m canids.detect --ratio 0.9    # しきい値を変える
```
