# セキュリティ報告書

キッズあそびランド（kids-play）の14日間（2026-10-08〜10-28）で行ったセキュリティの活動をまとめる。

- 対象：自分が管理するリポジトリ、アプリ、サーバーのみ
- IPアドレス、アカウントID、トークンなどの値は書かない
- 詳細の根拠は [threat-model.md](threat-model.md)（脅威 T-01〜T-23、対策 C-01〜C-26）と、各日の記録（[learning-log.md](../learning-log.md)）

## 1. まとめ

- **守ったもの**：いちばん大事な資産は「子どもの絵と声」（A1）。設計の段階で、絵と声が端末の外へ出る経路をつくらなかった（公開サーバーへの保存なし、Androidアプリはインターネットの権限なし、サーバー保存は PC の中だけで既定は無効）
- **やり方**：データフロー図と STRIDE で脅威を洗い出し（2日目の 12件 → 最終 23件）、対策ごとに「確認方法（証拠）」を決めて、テスト・画面なしのブラウザ・外からの診断で確かめた
- **結果**：今の時点で、CodeQL・Dependabot・Secret scanning の未対応の警告は 0件。CI は直し方のある CRITICAL の脆弱性で出荷（GHCR への push）を止める。AWS 版は SSL Labs A+、ZAP のベースラインで FAIL 0 を確かめたあと、14日目に片付けた
- **気づき**：脅威の半分近くは、机上の初版ではなく、作る途中で見つかった（保存、PWA、Androidアプリ化、コンテナ、自動デプロイ、片付け）。また、外の攻撃者だけでなく、開発に使う AI エージェントの誤操作（T-16、6日目に実際に起きた）も脅威として扱う必要があった
- **残るリスク**：5章。どれも理由を書いて受け入れた

## 2. 脅威分析の要約

詳細は [threat-model.md](threat-model.md)。

## 5. 残るリスク

| # | リスク | 受容する理由／今後の対応 |
|---|---|---|
| R-1 | 端末の同期・バックアップで、子どもの絵が端末の外に出る（T-13） | アプリの外の設定なので、アプリでは止められない。README の保護者向けの説明で注意を促す |
| R-2 | AWS アカウントに長く使う認証情報（IAM ユーザーのパスワード）がある（T-21） | AWS の推奨は一時的な認証情報（フェデレーション）だが、IAM Identity Center で権限を配るには Organizations が要り、使うと無料プランが有料プランに上がるため使わない。MFA を付け、アクセスキーは作らない。発展で使わなくなったらアカウントを閉じる |
| R-3 | GHCR のイメージが公開（T-19） | 中身は公開リポジトリと OS・Python の部品だけ。イメージに入るものを `.dockerignore` の許可リストで制限している。署名と来歴は16日目に足す |
| R-4 | Dependabot #70（Python 3.15、nginx 1.31 など）を見送っている | 版の上がり方が大きく、CI は起動まで確かめないため。手元で動かして確かめてから判断する |
| R-5 | AI エージェントの承認を、人が内容を読まずに許可する（T-16） | 仕組み（deny、ask、USB を抜く）を重ねたうえで、最後は人の注意に頼る。承認の画面ではコマンドの対象を読む |
| R-6 | 秘密の値を、画面の写しで会話に貼ってしまう（13日目の DuckDNS の token） | 作り直して無効にした。画面を貼る前に、秘密の値が写っていないかを見る |
| R-7 | Androidアプリのリリース版で、WebView のデバッグ接続が有効のまま（C-21 (6)） | リリース版を作っていない。作るときに無効であることを確かめる |

## 6. ISO/SAE 21434 との対応表

| ISO/SAE 21434 | 車載での内容 | このプロジェクトでの対応 | 共通点 | 違い |
|---|---|---|---|---|
| 5章 組織のサイバーセキュリティ管理 | 方針、規程、文化 | CLAUDE.md のルール、[SECURITY.md](../../SECURITY.md) | ルールを文書にし、道具（Hook、deny）で守らせる | 1人なので、役割の分離（作る人と承認する人）を、PR とレビュー用のサブエージェントで代わりにした |
| 6章 プロジェクト依存の管理 | サイバーセキュリティ計画 | docs/plan.md の日別のセキュリティ作業 | 開発の各段階に、セキュリティの作業を前もって割り当てた | 計画は日単位。車載のような成果物の審査（アセスメント）はない |
| 7章 分散開発 | サプライヤー管理（CIA） | 依存パッケージ、ベースイメージ、GitHub・AWS との責任分界 | 部品を固定し、更新は人が差分を確かめる | サプライヤーと契約を結べない。オープンソースの部品は「選ぶ・固定する・監視する」しかできない |
| 8章 継続的活動 | 監視、脆弱性分析・管理 | Dependabot、CodeQL、Trivy、Secret scanning、npm audit | 自動で毎回・毎週確かめる | 車両の監視（VSOC）に当たるものはない。対象はコードと部品だけ |
| 9章 コンセプト | アイテム定義、目標、コンセプト | threat-model.md の資産、信頼境界、対策 | 信頼境界がアイテムの境界に当たる | Web では境界の外（ブラウザ、他人のサーバー）が広い |
| 10章 製品開発 | 設計、実装、検証 | 安全なコード、テストを先に書く、レビュー、CI のテスト | 対策ごとに確認方法（証拠）を決めた | 形式的な検証の文書はない。テストと記録で代わりにした |
| 11章 妥当性確認 | 車両レベルでの確認 | ZAP、SSL Labs、画面なしのブラウザで外への通信0件、実機での録音 | 作ったものを外から攻撃者の目で確かめた | 侵入テストは自動のベースラインだけ。専門家の診断はしていない |
| 12章 生産 | 鍵の書き込み、生産管理 | 署名鍵の管理、CI/CD、OIDC（鍵を置かないデプロイ） | 出荷の経路から長く使う鍵をなくした | 物理的な生産はない。CI が生産ラインに当たる |
| 13章 運用・保守 | インシデント対応、更新（OTA） | 自動デプロイ、unattended-upgrades、証明書の自動更新、DuckDNS の token の作り直し | 更新を自動にし、漏れたら失効させた | OTA の代わりに、サーバーへの自動デプロイと、ブラウザの再読み込み |
| 14章 廃棄 | サポート終了、廃棄 | AWS の片付け（T-23、C-26） | 廃棄の順番を設計した（名前 → サーバー → IP → 権限） | 車両の廃棄より短い時間で終わるが、DNS の残り物という Web に特有の危険がある |
| 15章 TARA | 脅威分析とリスク評価 | threat-model.md | 資産 → 脅威 → 影響度 × 起こりやすさ → 対応方針 | 攻撃の実現可能性を3段階に簡略化。インターネットに公開するので「機会」は常に高い |

関連：

- **UN-R156（ソフトウェア更新）**：更新の完全性と真正性。ここでは CI で検査したイメージだけを push し、OIDC で引き受けたロールで、決まった命令書だけを送った。イメージの署名と来歴は16日目に足す（Uptane に近い考え方）

## 7. 動画の公開で行った確認（14日目）

- 素材④（13日目の画面録画）に、AWS の IAM の画面（ロールの ARN にアカウント ID）、秘密の設定値の画面、個人のニュースの画面が入っていた。使う区間を選び、画面の上のタブとアドレスバーを切り取った
- 書き出した動画から、Claude がコマを取り出して確かめ、学習者が音を出して全体を確かめた
- 動画は PR の添付として公開した。公開リポジトリの添付は、ログインなしで誰でも見られる（GitHub 公式）。上の確認のうえで公開した
- スマホのホーム画面の画像（壁紙に家族の写真）が、リポジトリの直下に gitignore されないまま置かれていた。コミットする前に、リポジトリの外へ移した
