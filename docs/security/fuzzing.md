# ファジングと静的解析、Rust での書き直し（17日目、KIDS-55）

題材は、自作の小さな TLV パーサー（[practice/tlv/](../../practice/tlv/)）。会社のコードやデータは使っていない。
kids-play の本体ではなく、車載の受信処理（診断メッセージの解析など）に近い形の練習用のコード。

## 仕様

- 1つのレコードは「種類（1バイト）| 長さ（2バイト、ビッグエンディアン）| 値」。これがバッファの終わりまで並ぶ
- `tlv_parse`：レコードを最大16個まで読む。`tlv_get_string`：指定した種類の値を、最後に NUL を付けて固定長の配列に写す

## 意図して入れたバグ

初版によくある書き方を再現するため、**1つだけ意図してバグを入れた**（ファザーが見つけられるかを確かめるため）。

- [tlv.c](../../practice/tlv/c/tlv.c) の `tlv_get_string` の長さの検査を `length > dst_size` にした。正しくは `length >= dst_size`（最後の NUL の分の1バイトが要る）
- ふつうのテスト（[test_tlv.c](../../practice/tlv/c/test_tlv.c)）は、境界値（値の長さ ＝ 書き込み先の大きさ）の入力がないので、このバグがあっても通った

## 結果

| 手段 | 道具 | 結果 |
|---|---|---|
| ふつうのテスト | clang 18 ＋ ASan / UBSan | 通った（バグを見つけられない） |
| ファジング | libFuzzer ＋ ASan / UBSan | **起動直後に発見**。`stack-buffer-overflow`、`WRITE of size 1`、[tlv.c](../../practice/tlv/c/tlv.c) の NUL を書く行 |
| 静的解析 | cppcheck 2.13（warning、style、performance、portability） | 直す前も直したあとも **指摘0件**（見つけられない） |
| 静的解析 | CodeQL（GitHub） | PR で確かめる（下の「残っていること」） |
| Rust 版 | rustc 1.99.1 | 同じ5つの入力と期待、回帰の入力が通る。同じ誤りを書くと、黙って壊さず panic で止まる |

### ファザーが見つけた入力

```
0b 00 00                     種類 0x0b、長さ 0
00 00 10 00 00 … 00          種類 0x00、長さ 16、値 16バイト  ← name[16] に 16バイト ＋ NUL で17バイト目に書く
00 00 00 …                   長さ 0 のレコードが続く
01 00 00                     種類 0x01、長さ 0
00 00 02 62 63               種類 0x00、長さ 2、値「bc」
```

ハーネスは、見つかった種類ごとに `tlv_get_string` を呼ぶ。種類 0x00 では最初のレコード（16バイト）が選ばれ、そこで書き込みがはみ出した。

- 原因：値16バイトのあとに NUL を書くので、16バイトの配列の外（17バイト目）に1バイト書いた
- 修正：検査を `length >= dst_size` にした
- 再発の防止：この入力を [regress/crash-get-string-nul-off-by-one.bin](../../practice/tlv/regress/) として残し、`./run.sh test` で毎回試す
- 回帰テストが効くことの確認：直す前のコードに戻した写しでは、この入力で同じ `stack-buffer-overflow` が出た。直したあとは出ない
- 直したあとのファジング：120秒、約1億回（101,787,926回）でクラッシュ0件

### cppcheck が見つけられなかった理由

長さの値は、実行時の入力（ファザーの作ったバイト列）から来る。静的解析は、コードを読むだけで「どんな入力でも安全か」を判断するので、入力の値と配列の大きさの関係を追い切れないと、警告を出さない。誤検知を減らすため、確かでないものは出さない作りになっている。
実行して確かめるファジングと、読むだけの静的解析は、得意なことが違うので、両方を使う。

### C と Rust の比較

| 観点 | C | Rust |
|---|---|---|
| 範囲の外への書き込み | 黙って隣のメモリを壊す（ASan を付けたときだけ見つかる） | 実行時に必ず止まる（`index out of bounds` の panic） |
| 入力の長さの検査 | 自分で書く。引き算と足し算のあふれにも気をつける | `split_at_checked` が足りなければ `None` を返し、範囲の外は読めない |
| 値の指す先（借用） | ポインター。入力のバッファを先に解放すると、解放後の利用になる | 借用。入力のバッファより長く使うと、コンパイルが通らない |
| 残るもの | 論理の誤り（長さの比べ方）は両方に残る | 同じ。Rust でも `>` と書けば誤りだが、メモリの破壊ではなく停止になる |

Rust に変えても論理の誤りは消えないが、「黙ってメモリを壊す」から「止まる」に変わる。車載では、止まることも安全上の問題になりうるので、panic を起こさない書き方（`get` で `Option` を受けるなど）と、テストやファジングは引き続き要る。

## 21434 と TARA との対応

- ファジングは、ISO/SAE 21434 の製品開発の段階の「統合と検証」で行う脆弱性テストにあたる。今回のように、ふつうのテストでは見つからない境界の誤りを見つける
- TARA では、外部から入力を受けるパーサーは攻撃の入口になる。ファジングは、その攻撃経路が実際に使えるか（実現可能性）を確かめる材料になる
- メモリ安全な言語への移行は、CISA などが推奨している。今回の比較は、その効果（破壊から停止へ）と限界（論理の誤りは残る）の両方を示す

## 再現の手順（WSL の Ubuntu で実行）

```bash
sudo apt install -y clang libclang-rt-dev cppcheck   # コンパイラー、ファザーとサニタイザー、静的解析の道具
cd practice/tlv/c
./run.sh test        # ふつうのテストと回帰の入力（ASan / UBSan つき）
./run.sh fuzz 60     # 60秒ファジングする。見つけた入力は build/crash-*
./run.sh check       # cppcheck
cd ../rust && cargo test   # Rust 版（rustup の minimal で入れた）
```
