# ML-KEM のハイブリッド鍵交換の計測（19日目）

- 日付：2026-11-04（KIDS-63）。脅威分析の T-31、対策 C-34
- 道具：[tools/pqc/](../../tools/pqc/)（計測と集計は Python と DuckDB、サーバーは `compose.yaml` の nginx）
- 暗号の一覧（CBOM）：[cbom.md](cbom.md)

## 何を比べたか

TLS 1.3 のハンドシェイクで、鍵交換の方式だけを変えて、時間と通信の量を比べた。

| 組み合わせ | クライアント | サーバー（nginx の入口） | 期待する方式 |
|---|---|---|---|
| hybrid | ハイブリッド（OpenSSL 3.5 の既定。ML-KEM と X25519 の両方を提案） | 8443：`X25519MLKEM768` だけ | X25519MLKEM768 |
| classic | X25519 だけ | 8444：`X25519` だけ | X25519 |
| hybrid-client-classic-server | ハイブリッド | 8444：`X25519` だけ | X25519 |

- サーバー：`nginx:1.31.8-alpine`（OpenSSL 3.5.9。`nginx -V` で確認）。セッションの再開は無効にし、毎回、最初から鍵交換をさせた
- クライアント：Python 3.14.10（OpenSSL 3.5.9）。Python の ssl には「決まった方式」を返す関数がないので、サーバーの最初の返事（ServerHello）の key_share の番号を読んで確かめた（`0x11EC` が X25519MLKEM768、`0x001D` が X25519）
- 時間：TCP の接続のあとから、ハンドシェイクの終わり（クライアントの Finished を送るまで）。PC の中の通信なので、ネットワークの遅れは入らない
- 回数：6回 × 各組み合わせ。最初の回は 200回、2〜6回目は `/loop`（2分ごと）で 100回ずつ。組み合わせは交互に並べ、PC の負荷の揺れが片方に偏らないようにした

## 結果（DuckDB の SQL で集計。各 700回）

| 組み合わせ | 決まった方式 | 回数 | 中央値（ms） | 平均（ms） | 95%（ms） | 送った量（バイト） | 受け取った量（バイト） | やり直し |
|---|---|---|---|---|---|---|---|---|
| classic | X25519 | 700 | 2.07 | 2.15 | 2.85 | 315 | 791 | 0 |
| hybrid | X25519MLKEM768 | 700 | 2.38 | 2.47 | 3.28 | 1549 | 1879 | 0 |
| hybrid-client-classic-server | X25519 | 700 | 2.10 | 2.21 | 3.00 | 1549 | 791 | 0 |

回ごとの中央値（ms）：

| 回 | classic | hybrid | 差 |
|---|---|---|---|
| 1（200回） | 2.04 | 2.37 | +0.33 |
| 2 | 2.08 | 2.39 | +0.31 |
| 3 | 2.05 | 2.34 | +0.29 |
| 4 | 2.10 | 2.47 | +0.37 |
| 5 | 2.26 | 2.45 | +0.19 |
| 6 | 2.12 | 2.34 | +0.22 |

集計に使った SQL（[analyze.py](../../tools/pqc/pqc_bench/analyze.py) の一部）：

```sql
SELECT scenario, count(*) AS n, median(elapsed_ms) AS median_ms,
       quantile_cont(elapsed_ms, 0.95) AS p95_ms,
       avg(bytes_out) AS avg_bytes_out, avg(bytes_in) AS avg_bytes_in
FROM measurements
GROUP BY scenario;
```

集計の前に、「期待と違う方式で決まった記録」を SQL で探し、1件でもあれば止める（0件だった）。

## 分かったこと

1. **増えるのは主に通信の量で、時間はわずか**：ハイブリッドは、送る量が +1234 バイト、受け取る量が +1088 バイト。ML-KEM-768 の公開鍵（1184 バイト）と暗号文（1088 バイト）の大きさとほぼ同じ。時間は中央値で +0.3 ms（約15%）。インターネット越しでは、往復の時間（数十 ms）に埋もれる
2. **量は毎回同じ、時間は揺れる**：量は仕様で決まるので6回とも同じ。時間は回ごとに +0.19〜+0.37 ms と揺れたが、ハイブリッドのほうが遅いことは毎回同じだった
3. **PQC に対応したクライアントは、相手が未対応でも大きな ClientHello を送る**：3行目。両方の鍵を最初から送るので、やり直し（HelloRetryRequest）は0回で済むが、送る量は常に大きい
4. **気づかずに従来の方式へ戻ることはない**：X25519 だけのクライアントは、ハイブリッドだけの入口につながらなかった（結合のテスト）。逆に、サーバーの設定で `X25519MLKEM768` の名前を外すと、エラーなしで従来の方式だけになる。名前を書いたかではなく、決まった方式を確かめる必要がある（C-34 (3)）
5. **公開中の kids-play（GitHub Pages）は、すでにハイブリッドに対応していた**：同じ道具で `hayato-f110.github.io:443` に1回ずつつないだ。ハイブリッドのクライアントでは X25519MLKEM768、X25519 だけのクライアントでは X25519 で決まった。Chrome と Edge は既定で ML-KEM を提案するので、ブラウザからの閲覧はハイブリッドで守られている見込み

## 車載との対比

- CAN（8バイト）や CAN FD（64バイト）では、1184 バイトの鍵は1フレームに入らない。車内の通信に PQC を入れる難しさは、計算より帯域にある。18日目の SecOC で MAC を切り詰めたのと同じ問題
- 車の外の通信（テレマティクス、OTA）は TLS なので、今日と同じハイブリッドを使える。車は15年以上使うので、「いま記録して、将来解読する」攻撃（T-31）への備えが先に要る
- ECU の HSM が ML-KEM や ML-DSA を計算できるかは、出荷のときに決まる。あとから入れ替えられるように（クリプトアジリティ）、どこで何の暗号を使っているかを CBOM で管理する

## 再現の手順（tools/pqc で）

```powershell
uv run python -m pqc_bench.certs            # 試験用の証明書を .certs/ に作る（Git の外）
docker compose up -d                        # nginx を 127.0.0.1:8443 と 8444 で起動
uv run python -m pqc_bench.measure --count 100
uv run python -m pqc_bench.analyze          # 方式ごとの集計
uv run python -m pqc_bench.analyze --by-run # 回ごとの中央値
docker compose down                         # 片付け
```
