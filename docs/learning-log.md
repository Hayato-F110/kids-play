**2. PRを1本マージ（実績は5本：PR #1〜#5）**

PR（プルリクエスト）とは：ブランチで行った変更を「main に取り込んでください」と依頼し、差分を確認してから取り込む、GitHubの仕組み。車載開発でいえば、変更をトランクに入れる前のレビュー依頼と承認の記録に当たる。1人の開発でも、差分を見直す機会と、「いつ・何を・なぜ入れたか」の記録が残る。

確かめたこと：GitHubで5本とも Merged／Jiraの課題の「開発」欄にコミットとPRが表示される／PC側の main が GitHub と同じ状態。

| 技術 | 何をするものか | 使った場所 |
|---|---|---|
| ブランチ | main を汚さずに作業する枝。「次のコミットをどこに積むか」の札 | `git switch -c <種別>/KIDS-<番号>-<説明>` |
| コミットと push | コミットはPC内の記録、push はGitHubへ送ること | `git add` → `git commit` → `git push -u origin <ブランチ>` |
| プルリクエスト | 変更の取り込みを依頼し、差分を確認して main に入れる | GitHubの Files changed → Merge pull request |
| マージ後の同期 | GitHubの main を PC に取り込み、不要なブランチを消す | `git switch main` → `git pull` → `git branch -d` |
| 積み上げたブランチ | あるブランチの上に次のブランチを作る。下から順にマージする | KIDS-9 の上に KIDS-10 |
| stash | 書きかけの変更を一時的に退避する | 別のブランチへ移るとき |
| JiraとGitHubの連携 | ブランチ名とコミットに課題キーを入れると、課題に自動で表示される | `KIDS-9 feat: …` |
| スクラムのバックログ | 課題を「未着手 → 完了」と動かし、進み具合を見えるようにする | KIDS-6〜KIDS-11 を完了 |

### 学んだこと3行

1. CSSは「基本を先に書き、条件に合うときだけ上書きする」。`@media` の中だけに書くと、条件に合わない画面では何も効かない
2. JavaScriptのモジュールは、`export` したものだけが外から使える。状態を持つ変数を公開せず関数だけを公開するのは、Cの static 変数と公開関数の関係と同じ

### つまずいたこと（原因と解決）

- `python -m http.server` を実行するとターミナルが戻らない → 止まっているのではなく、要求を待ち続けるサーバー。別のターミナルを開いて作業し、止めるときは Ctrl+C
- メニューを横長の画面用にだけ書いたら、縦長で巨大なボタンに戻った → 共通の指定を `@media` の外に出した
- 消音ボタンが動かず、Console に「export がない」というエラー → 読み込む側が期待する関数を、読み込まれる側がまだ公開していなかった。Cのリンクエラーに近いが、ブラウザが読み込んだ時点で出る
- 上に積んだブランチ（KIDS-10）のPRは、下のブランチ（KIDS-9）を先にマージしないと、両方の変更が差分に出る → マージの順番を守った
- マージ済みのブランチを `git branch -d` で消せなかった → 今いるブランチを基準に判定されるため。main に入っていることを確認してから削除した
- ヒントだけでは書けない部分があった（CSS Grid、mute.js）→ 具体的なコードを示してもらう形に切り替えた。3日目のピアノで、同じ技術をもう一度自分で書く

### 学んだこと3行

1. AIエージェントの手は、プロジェクトのフォルダの外にも届く。フォルダの制限はファイルの読み書きにだけ効き、コマンドは、PCにつながるものすべて（USBでつないだスマホを含む）を操作できる
2. 取り返せない操作は、AIの注意や自動の判定に任せず、仕組み（deny、人の承認、バックアップ）で止める。機能安全で、1つの層を信じずに独立した層を重ねるのと同じ
3. AIの最初の案に「なぜ」と問い直すと、より良い案が出ることがある（npm audit の直し方、素材②が要るかどうか）。納得できない点は、そのまま進めずに聞く

### 今日学んだこと（3つの分類）

**流行の技術**

- Capacitor：Web アプリを、Android の WebView に包んでアプリにする。Web の画面から Java の機能を呼ぶ「橋」を、必要な分だけ作れる。既存の Web 資産をアプリとして配る場面で使える
- Gradle と Java の版：ビルドの道具は、対応する Java の版が決まっている。プロジェクトごとに版を指定して、複数の版を共存させる。車載で、コンパイラの版をプロジェクトごとに固定するのと同じ
- 画面の端まで広がる表示（Android 15）：アプリは、端末が教える安全な余白の分だけ、内側に寄せる
- WebView はブラウザではない：ダウンロードを受け取らないなど、ブラウザが当たり前に行うことを、アプリ側で用意する必要がある
- 保存領域と復元：内蔵は暗号化されていて、消すと戻せない。microSD（FAT32）は、目次から消えるだけで、中身は上書きされるまで残る。スマホ経由（MTP）はファイル単位の命令しかなく、復元にはカードを直接読む必要がある
- 学べなかったこと：なし。ただし、Android Studio は構成を開いただけで、ビルドと転送はコマンドで行った

**Claudeの使い方**

- MCP：Claudeに、外部の道具を後付けする。Playwright MCP で、ブラウザを開く・押す・測るが、道具の呼び出しになった。リポジトリに置いた設定は、人が承認するまで動かない。仕事では、チケット管理や試験装置をつなぐ形に使える（読むだけの権限から始める）
- 権限の3段階（deny、ask、allow）：今日は、事故のあとに、adb の危険な操作を deny に、実機に届くコマンドを ask にした。壊せる相手をつないでいる間は、人が1つずつ承認する
- 自動で可否を決めるモードの限界：誤った削除のコマンドを通した。任せきりにしない
- 会話を閉じて開き直すと、設定（MCP）が読み込まれ、会話の内容は残る
- 頼み方：実機でしか分からないこと（音、指、見た目）は、番号を付けた一覧で頼まれ、番号で答える形が速かった。AIが端末に作ったもの・消したものは、記録に残させる

**セキュリティ**

- AIエージェントの誤操作を、脅威として扱う（T-16）。これまでの脅威分析は、外からの攻撃者だけを想定していた。TARA で言えば、攻撃経路「エージェント → シェル → adb → 端末」と、資産「アプリと関係のない個人のデータ」（A6）が抜けていた
- USBデバッグは、信頼の境界をまるごと開ける。車載で、診断のセキュリティアクセスを解除した状態に当たる。使わないときは閉じる
- Android の最小権限：権限は、なし。バックアップと機種変更の転送を無効にし、使っていない入口（FileProvider）を外した。`allowBackup` だけでは足りず、追加の規則が要ることを、公式ドキュメントで知った
- Web から呼べる入口の入力検証：ファイル名の形、大きさ、PNG であることを、Java 側で確かめる。境界をまたぐデータは、受け取る側で検証する
- サプライチェーン：版を固定する（Capacitor、Playwright MCP）。`npm audit` の指摘は、影響を調べたうえで、不整合を作らない直し方を選ぶ
- ブランチ保護：main への直接 push と強制 push を、サーバー側で止めた。お願いを、仕組みに変えた
