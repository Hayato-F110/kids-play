**2. PRを1本マージ（実績は5本：PR #1〜#5）**

PR（プルリクエスト）とは：ブランチで行った変更を「main に取り込んでください」と依頼し、差分を確認してから取り込む、GitHubの仕組み。車載開発でいえば、変更をトランクに入れる前のレビュー依頼と承認の記録に当たる。1人の開発でも、差分を見直す機会と、「いつ・何を・なぜ入れたか」の記録が残る。

確かめたこと：GitHubで5本とも Merged／Jiraの課題の「開発」欄にコミットとPRが表示される／PC側の main が GitHub と同じ状態。

| 技術 | 何をするものか | 使った場所 |
|---|---|---|
| ブランチ | main を汚さずに作業する枝。「次のコミットをどこに積むか」の札 | `git switch -c <種別>/KIDS-<番号>-<説明>` |
| コミットと push | コミットはPC内の記録、push はGitHubへ送ること | `git add` → `git commit` → `git push -u origin <ブランチ>` |
| プルリクエスト | 変更の取り込みを依頼し、差分を確認して main に入れる | GitHubの Files changed → Merge pull request |
| マージ後の同期 | GitHubの main を PC に取り込み、不要なブランチを消す | `git switch main` → `git pull` → `git branch -d` |
| 積み上げたブランチ | あるブランチの上に次のブランチを作る。下から順にマージする | KIDS-9 の上に KIDS-10 |
| stash | 書きかけの変更を一時的に退避する | 別のブランチへ移るとき |
| JiraとGitHubの連携 | ブランチ名とコミットに課題キーを入れると、課題に自動で表示される | `KIDS-9 feat: …` |
| スクラムのバックログ | 課題を「未着手 → 完了」と動かし、進み具合を見えるようにする | KIDS-6〜KIDS-11 を完了 |

### 学んだこと3行

1. CSSは「基本を先に書き、条件に合うときだけ上書きする」。`@media` の中だけに書くと、条件に合わない画面では何も効かない
2. JavaScriptのモジュールは、`export` したものだけが外から使える。状態を持つ変数を公開せず関数だけを公開するのは、Cの static 変数と公開関数の関係と同じ
3. 脅威分析は、設計が固まる前に行うと対策を安く入れられる（音の出口を1か所にまとめた例）。STRIDEは要素ごとに6分類を当てる方法で、TARAの脅威シナリオの洗い出しに使える

### つまずいたこと（原因と解決）

- `python -m http.server` を実行するとターミナルが戻らない → 止まっているのではなく、要求を待ち続けるサーバー。別のターミナルを開いて作業し、止めるときは Ctrl+C
- メニューを横長の画面用にだけ書いたら、縦長で巨大なボタンに戻った → 共通の指定を `@media` の外に出した
- 消音ボタンが動かず、Console に「export がない」というエラー → 読み込む側が期待する関数を、読み込まれる側がまだ公開していなかった。Cのリンクエラーに近いが、ブラウザが読み込んだ時点で出る
- 上に積んだブランチ（KIDS-10）のPRは、下のブランチ（KIDS-9）を先にマージしないと、両方の変更が差分に出る → マージの順番を守った
- マージ済みのブランチを `git branch -d` で消せなかった → 今いるブランチを基準に判定されるため。main に入っていることを確認してから削除した
- ヒントだけでは書けない部分があった（CSS Grid、mute.js）→ 具体的なコードを示してもらう形に切り替えた。3日目のピアノで、同じ技術をもう一度自分で書く
